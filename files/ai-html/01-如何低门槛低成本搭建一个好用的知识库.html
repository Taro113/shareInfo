一、为什么要建知识库

1.1 知识库的清晰定义

知识库（Knowledge Base for AI Agent）：一个结构化的、可语义检索的外部长期记忆系统。 它存储领域相关的稳定知识（规范、经验、接口文档、架构说明），在 Agent 执行任务时按需注入精准上下文，以约束生成行为、抑制幻觉、提升输出质量。

它不是数据库（不存事实数据）、不是模型（不负责推理）、不是工作记忆（不存临时对话）。它是 Agent 的「领域专业记忆」。

用一个更直观的类比：

角色类比存什么
大模型（LLM）人类大脑的通用推理能力无法更新的「训练记忆」
知识库（RAG）你桌上的专业参考书领域知识、规范、经验（可更新）
数据库（DB）业务台账 / 数据记录有时效的事实数据（需精确查询）
工作记忆（Context Window）短期工作便签当前对话/任务的临时上下文

1.2 业界知识库建设相关调研分析

知识库的价值已经不是"是否需要建"的问题，而是"如何建好"的问题。

在启动知识库方案设计之前，我们系统性地调研了国内外知识库应用的建设实践。业界知识库建设主要停留在工具/平台层面（司外如阿里云百炼、Coze、Cursor等，司内Block AI已经做的非常成熟，它们解决的是向量存储、混合检索、Embedding 优化等基础能力问题），但真正能用好这些工具构建高质量知识库应用的组织仍是少数。我们的重点不是重复造轮子，而是填补工具与实际应用之间的鸿沟——让普通团队也能低门槛、低成本地构建真正可用的知识库应用。

1.4 现实困境：建了，但质量差、成本高、用处小

知识库的必要性已无争议。但实际落地中，团队普遍面临三类核心困境：

  • 建不起来：传统建库需要人工梳理大量信息，用户不知道该写什么、怎么分层，冷启动门槛高；建好之后维护成本同样高昂，大量项目的知识库久而久之成为「死库」
  • 质量靠不住：知识库里充斥过时、冗余、冲突的内容；踩过的坑和复盘结论散落各处无法沉淀；多人多项目各建各的，重复建设或存在内容冲突
  • AI 用不好：知识条目粒度粗、结构乱，AI 召回噪声大；大量堆砌知识反而让 context 过载，token 消耗高、生成质量下降

    • 所以我们的目标是建设一套高质量、低成本、AI 友好具备全生命周期管理的知识库整体解决方案。

    二、"好用"的知识库的定义

    2.1 什么是"好"的知识库？

    知识库的评判标准目前尚无单一权威标准，但业界已形成几套主流框架，我们采用RAGAS 评估体系（学界+工业界最广泛采用）：

    来源：Shahul Es 等，论文《RAGAS: Automated Evaluation of Retrieval Augmented Generation》（2023），arXiv:2309.15217

    ⚠️ 此表格含合并单元格，以下为简化显示（完整结构请通过 getDocumentXml 查看）

    RAGAS 指标定义评的是
    Faithfulness 可信度**可信度：**生成答案与检索到的知识的一致程度，非幻觉产生。知识语义完整、无歧义；接口文档与代码实现一致；规范描述明确可执行（"必须使用 XX 格式"而非"尽量保持一致"）知识库的事实可信度
    Answer Relevancy 答案相关性**精准：**检索到的上下文中真正被用到的占比。查询时只返回真正相关的内容，取决于知识粒度（chunk 大小合适）、结构化程度（关系显式标注）、索引质量（Embedding 模型选型），生成答案与问题的相关程度。你的回答是不是在回答用户问的那个问题，有没有跑题。知识库内容的针对性
    Context Precision 上下文精准度知识库的精准度（低噪音）
    Context Recall 上下文召回率**完整：**回答所需知识是否都被召回。核心模块、关键接口、重要规范都有对应知识文档。覆盖率低会让 Agent 在关键节点"两眼一抹黑"，被迫依赖模型训练记忆，质量和稳定性无法保证知识库的完整性

    同时我们也要保证知识新鲜（时效性），如知识与代码库/业务实际保持同步，过期知识比没有知识更危险——它会以"权威"的面目误导 Agent。需有明确的更新触发机制（文件保存触发 / 定时同步 / 增量更新）

    一句话总结：好的知识库 = 可信度（Faithful）× 新鲜（Fresh）× 精准（Precise）× 完整（Complete）。四个维度缺一不可：可靠是底线，新鲜是生命线，精准是效率线，完整是能力线。

    2.2 什么是“好用”的知识库？

    好用 = 好的知识 + 好的落地应用方案

    知识库除了做好高质量（好）以外，还需要体系化的使用配套才能发挥出知识库最大的潜力，我们关注到知识库应用阶段需要解决的关键问题有：

    关键问题为什么需要
    使用成本**低成本是知识库从"试点"走向"规模化"的唯一通路**——高质量的知识库如果建设门槛高、维护负担重，就只会停留在少数项目，无法成为团队级基础设施
    团队友好性团队友好型知识库能够额外带来： - **集中管理、统一运营**：基于团队维度（外卖终端团队）统一管理和运营知识，**避免知识库建设进入“先污染后治理”的无序发展阶段** - **沉淀、复用标准知识**：最大程度减少知识的重复建设，提升知识库建设效率，并渐进建设一套标准化的AI 知识库资产，驱动团队AI实践标准统一，形成**可传承、可演进的知识库体系** - **规模化效应**：基于统一的知识库建设，**能够在团队内快速复制横向的 AI 探索及实践优秀案例，加速 AI 化改造**
    harness engineering结合在 AI Agent 时代，知识库并不是孤立存在的，好用的知识库是融合harness engineering的最佳工程实践，知识库作为Agent 运行时的可检索长期记忆层，**给 Agent 提供消费的结构化上下文和约束、反馈层的运行机制范式**
    全生命周期管理知识库具备强时效性，“好”的知识库需要“与时俱进”，以确保知识库的时效性、准确性、完整性，知识库的保鲜本身也是工程量巨大的课题；围绕知识库的全生命周期建立配套的知识管理方案确保知识的演进能够融入到现有的研发流程体系中，而不是成为依赖开发者自觉驱动的产物和开发时的“累赘”，**全生命周期的知识库管理方案确保“好”的知识库“持续好用”**

    3.1 生成“好”的知识

    3.1.1 知识分层（可信度、完整）

    公司级知识：所有项目必须遵守的底层规范与能力支撑，司内统一技术栈选型、基建平台接入规范、成熟第三方技术栈的使用约定

    项目级知识：支撑具体业务场景的领域知识沉淀，服务于开发、测试、运维和新人上手。（技术栈清单与项目规范、工程架构、工程知识、业务流程介绍、运维信息、新人入门指引。）

    3.1.2 知识AI 友好度（精准）

    知识 AI 友好度三条核心规律：

  • 粒度决定质量：知识拆到"最小语义单元"，粒度过粗则检索噪声大，粒度过细则语义割裂
  • 关系比内容更值钱：显式标注知识关系，AI 才能从"找内容"升级到"理解关系"
  • 精准 > 全面，按需 > 全量：注入最相关的知识，而非塞满 context

    • 落实到知识库的组织方式，AI 友好体现在三个技术维度：

  • 知识图谱：显式标注实体关系（模块依赖、接口契约、规范引用），让 AI 从"找到内容"升级到"理解关系"，在 AI Coding / CR 等场景中能回答"哪些地方依赖这个接口"
  • 按需引入（渐进式披露）：细粒度知识拆分 + 分层索引，Agent 先加载摘要层，按需深入细节层，大幅优化 context 占用，避免"一次性全量注入"浪费 token
  • 结构化上下文注入（Harness 协同）：在 Harness Engineering 体系中，知识库向 Agent 提供四层结构化上下文——上下文层（背景知识）、约束层（规范与边界）、反馈层（历史经验）、状态桥接层（当前任务状态）。这比"把一篇文档塞进 prompt"精准得多

    • 直观类比：普通知识库像一堆扫描件——内容都在，但没有结构，AI 只能全文逐页搜。AI 友好的知识库像有标注的专业书籍——有章节索引、有关键词标注、有页边注释，AI 直接定位到最相关的段落

    📊 流程图（Drawio）：https://km.sankuai.com/api/file/cdn/2758494864/234546796912?contentType=0&isNewContent=false

    3.1.3 知识保鲜机制（新鲜）

    保鲜机制的本质是把知识库从"一次性建设"变成"持续运营"，通过事件驱动 + (AI+人工)审核 + 数据度量三板斧，确保知识始终可信、可用、可追溯。

    业界共识：不保鲜的知识库会迅速成为"毒库"——过期的接口文档、废弃的规范、已修复的 Bug 记录，会直接导致 AI 生成错误代码。无论自动化程度多高，企业级实践都保留人工审核环节，以防止"AI 生成的知识未经把关导致质量螺旋下降"。

    公司级知识库：由基建团队进行建设和更新，业务团队无需关注

    团队级知识库：由团队中的知识标准委员会进行沉淀更新

    项目级知识库：AI 自动触发更新 或 业务负责人主动更新

    3.2 如何让知识“好用”

    3.2.1 低成本

    传统知识库建设的高成本来自冷启动——需要人工整理架构文档、接口说明、编码规范，往往耗费数天才能形成可用的初始库，这是大多数团队"建了又弃"的根本原因。我们的目标是把冷启动成本压缩到分钟级，核心路径如下

  • 一句话启动，AI 自动生成初稿：用户只需输入项目名或仓库地址，AI 自动扫描代码结构、提取关键信息，生成结构化知识条目。用户做的只有一件事：确认或微调，而不是从零填写。
  • 缺失信息自动推导，不靠人工补全：AI 自动识别项目类型（后端服务 / 前端应用 / 基础库等），对于文档缺失的模块，基于代码自动推导描述，用"确认"代替"填写"，大幅降低人工介入门槛。
  • 存量知识自动复用，新项目不重复造轮子：建新知识库前，系统自动匹配已有的团队级/公司级知识库，可直接继承，避免同类信息重复录入。新项目手动选择拉取，存量资产最大化利用。
  • 越用越好：偏差自动沉淀，知识库持续生长，AI 使用过程中产生的纠偏（用户修正了错误答案）、踩坑复盘，自动转化为新知识条目入库，形成"用 → 纠偏 → 沉淀 → 更好用"的正向飞轮。知识库不需要人工定期维护，它会自己长大。

    • 📊 流程图（Drawio）：https://km.sankuai.com/api/file/cdn/2758494864/234546127593?contentType=0&isNewContent=false

    3.2.2 团队友好

    团队友好型知识库通过三大支柱构建团队级 AI 知识管理体系：

  • 集中管理·统一运营 — 以 Block AI 平台为统一载体，三层架构（公司/团队/项目）打通知识孤岛，配合 AI Linter 规范守护，从源头避免知识"先污染后治理"的无序困境。
  • 沉淀复用·标准知识 — 自动扫描存量识别可复用条目，K-Hub ID 化实现跨项目引用零冗余，公共知识一次沉淀、全团队受益，逐步构建可传承、可演进的标准化 AI 知识库资产。
  • 规模化效应·横向复制 — 基于统一知识库支撑全角色消费（研发/产品/运营/新人/AI），将优秀 AI 实践快速横向覆盖到其他项目，加速团队整体 AI 化改造进程。

    • 三者形成正向飞轮：集中治理防乱 → 沉淀复用提效 → 规模化放大价值 → 更多知识汇入 → 体系持续增强，最终实现知识不再孤岛、团队统一规范、AI 实践可传承可复制的目标。

    3.2.3 harness engineering 结合

    知识库和harness engineering 结合主要包含两个部分：

    1）AI主动共识harness engineering运行机制，约束解空间，包含两部分：

  • 由AI主动和用户澄清项目的约束（做什么、怎么做）：基于项目和需求维度和用户共识本次功能实现的拆分粒度[^功能必须拆分实现：单个功能点实现代码不能超过xx行代码之类的]，明确需求输入输出信息及禁止操作信息，功能点必须经过验收[^验收：必须经过lint、linter、功能自动验收【单侧】、人工验收]才可进入下一个功能点实现、需要用户提供哪些工具用于验收，由AI自主驱动帮助用户建设项目的harness 约束层；
  • 由AI主动和用户共识验收标准（做到什么程度算对）：在任务开始前，由AI主动发起和用户共识任务的验收标准及验收所需要的验收工具，引导用户进行验收工具的完善和harness反馈层搭建，比如：需要用户明确项目lint规范、需要引导并辅助用户搭建自动化测试工具等；

    • 2）终端harness engineering基建最佳实践在各团队的快速落地：团队AI coding长期实践中沉淀的基础规范、harness约束、统一约束及反馈层工具最佳实践能够快速复用和横向覆盖到终端内其他项目，实现harness engineering水位的整体提升；

    3.3 知识库工具的自我评测迭代

    针对3.1和3.2部分的内容，我们将相关能力skill化方便用户更低成本的落地使用（详见：“Skill一站式知识库创建、更新及全生命周期管理”）；但同时我们意识到AI时代伴随各业务的快速验证落地，所谓工具的“最佳实践”可能也会很快面临淘汰，需要建立了一套知识库工具的评测准入机制，来确保知识库方案也能够紧跟潮流、紧贴用户需求持续进行迭代和演进。

    为确保知识库工具能够持续生产高质量知识库，我们设计了分层的知识库工具评测体系：知识库质量评测和应用效果评测，知识库工具每一次版本迭代均需要经过严格的效果评测才能交付用户使用，避免靠“感觉”优化；前者是评估"知识库本身是否符合高标准"，后者则验证"知识库在具体场景用起来效果到底好不好"。举个栗子：研发在承接开发某个需求时，我们会关注代码写法、命名、代码组织合理性等等，本身是确保提交的是高质量代码；再比如除了高质量代码之外，我们还需要验证代码是否实现了需求的全部功能，是否有逻辑bug，是否明确按照PRD里的要求来实现对应功能等等。

  • 评测数据集构建：评测数据集是评测机制的基石。我们采用标准化格式：

}

    ground_truth人工审核标准答案必须准确、完整
    持续维护随知识库更新知识变更时同步更新评测集

    五、未来展望

    在落地节奏上，当前知识库项目在外卖终端组内小范围试运营，下一阶段我们期望能够期望把该方案打造成团队统一知识库方案，拿到规模化落地的效果验证和认知，后续在更大范围（跨职能团队、跨业务团队）内推进该方案，加速美团知识库统一方案的落地，进一步释放该方案的规模化效应，赋能更多业务、技术团队的AI探索应用。

    知识库迭代上，当前是从研发视角以工程纵向分层知识库出发建设知识的全生命周期管理机制，未来是探索从业务/工程/团队三级知识库横向解耦，通过 Relation 动态索引联通，打造不同视角（研发/PM等）多角色的知识拓扑视图。

    在能力建设部分，我们期望能够和司内公共服务团队紧密合作，尽快完成ORG层知识库内容的标准化对接，同时在应用层和司内优秀的AI coding workflow实践和基建提供团队合作，提供集成度更高、体验更加完整的知识库应用方案；最终目标是构建一个服务于各职能团队的自进化知识网络，Agent 每完成一次任务，经验自动沉淀、审核入库、反哺给所有团队成员，从"每次新手上路"变成"持续积累成长"。
