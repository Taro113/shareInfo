SDD 规范驱动开发：AI 协作范式与 spec-kit 工具实践

作者整理：2026-03-26

参考来源：业务需求 Spec Coding 实践路径、Spec Coding 研发范式应用、GitHub spec-kit、Microsoft Learn: SDD 工作流阶段

一、背景：为什么需要 SDD？

AI Coding 工具正在改变软件研发的工作方式。从 Vibe Coding（直觉驱动，拿起 Cursor 就开干）到 Spec Coding（规范驱动，先写规范再编码），体现了团队对 AI 协作质量的更高追求。

核心问题：当我们把一段模糊的 PRD 或者一句话需求丢给 AI，AI 其实并不能保证"正确理解"。缺失的业务知识、产品黑话、历史代码上下文，都是影响最终交付质量的隐患。Spec Coding 就是为了解决这个问题而生的。

二、核心概念：什么是 SDD（规范驱动开发）？

SDD（Spec-Driven Development，规范驱动开发） 的核心理念是：

先编写规范（Specification），再进行编码（Coding）。规范是真理的来源，代码是其表达方式。

参考 Specification (technical standard)) 的通识定义，Spec 可以涵盖：

Spec 类型说明
**需求规范**（requirement specification）描述用户需要什么，解决什么问题
**功能规范**（functional specification）系统应具备哪些行为和能力
**设计/产品规范**（design / product specification）架构方案、数据模型、接口契约

SDD 的三大目标：

  • 消除规范与实现之间的鸿沟：让规范可执行，直接驱动代码生成，保持两者同步
  • 提升开发效率和质量：自动化机械性工作，让开发者专注于创造性和批判性思维
  • 应对软件复杂性和快速变化：提供系统化方法管理复杂系统，支持快速迭代

    • 三、Vibe Coding vs Spec Coding：对比分析

    团队在选择工作模式时，应根据场景动态选择，而非非此即彼。

    3.1 核心对比

    维度Vibe Coding（直觉驱动）Spec Coding（规范驱动）
    **开发模式**跟着感觉走，探索式，"干中学"工程化管理，"计划后执行"
    **初始速度**极高，快速启动较慢，前期需投入规划
    **长期效率**可能因重构和返工降低减少返工，总体时间更短
    **可维护性**隐性知识，难以文档化显性知识，易于标准化
    **适用场景**原型验证、创意探索复杂业务、生产系统

    3.2 混合策略推荐

    场景维度最佳实践
    启动速度原型阶段用 Vibe，生产阶段用 Spec
    长期维护架构层面用 Spec，实现层面适度 Vibe
    创新突破探索阶段用 Vibe，验证阶段用 Spec
    团队协作接口规范用 Spec，内部实现用 Vibe
    风险控制关键路径用 Spec，边缘功能用 Vibe

    关键认知：Vibe Coding 和 Spec Coding 本质是两种不同的认知策略，不是对立面。推荐在项目不同阶段动态选择合适的方法。

    3.3 与传统开发范式的关系

    SDD 不是孤立的，它与传统范式可以搭配使用：

    传统范式与 SDD 的关系
    **TDD**（测试驱动）SDD 奠定基础，TDD 强制正确性；先写规范，再写测试，再写实现
    **BDD**（行为驱动）BDD 以用户场景触发，连接技术需求与业务目标；与 SDD 互补
    **DDD**（领域驱动）领域模型规范是 Spec 的重要组成部分
    **CFD**（契约优先）接口规范（适合前后端、跨服务对接）是 Spec 的一种

    四、SDD 的工作流阶段

    SDD 的工作流分为三个核心阶段，对应 spec-kit 的三个核心命令：

    模糊想法  →  [/specify]  →  PRD（需求规范）
PRD       →  [/plan]     →  实现计划（架构 + 数据模型 + 接口契约）
实现计划  →  [/tasks]    →  可执行任务清单
任务清单  →  [AI 编码]   →  代码实现
代码实现  →  [测试验证]  →  质量保证
反馈      →  [规范演进]  →  SDLC 循环

    阶段一：Specify（想法 → PRD）

    通过与 AI 的迭代对话，将模糊的想法转化为全面、结构化的产品需求文档。

  • AI 提问、识别边缘情况、定义验收标准
  • 重点强调"用户需要什么"和"为什么需要"，避免过早关注"如何实现"
  • 利用模板强制标记不明确之处 [NEEDS CLARIFICATION]
  • 自动管理版本控制

    • 阶段二：Plan（PRD → 实现计划）

    从已共识的 PRD 生成详细的实现计划，将业务需求映射到技术方案。

    产出物包括：

  • plan.md — 技术架构方案
  • data-model.md — 数据模型设计
  • contracts.md — API 接口规范

    • 阶段三：Tasks（实现计划 → 可执行任务）

    根据实现计划和相关设计文档，生成一个可执行的任务清单（Checklist）。

    遵循"测试优先"原则：

  • 先生成单元测试、集成测试、端到端测试
  • 确保 AI 生成的代码能够通过测试
  • 人工持续检查反馈，将信息补充到规范中驱动演进

    • 五、SDD 的 AI 协作范式核心思想

    spec-kit 揭示了 SDD 与 AI 协作的六大核心原则：

    5.1 规范即通用语言

  • 规范是主要产物，代码是其表达方式
  • 维护软件 = 演进规范

    • 5.2 可执行规范

  • 规范必须足够精确、完整、无歧义，以便生成正确代码
  • 避免"AI 读心术"——不要期待 AI 猜测你的意图

    • 5.3 持续精化

  • AI 持续分析规范的歧义、矛盾和漏洞
  • 持续改进，而非一次性产出

    • 5.4 研究驱动的上下文

  • 在规范过程中收集技术选项、性能影响、组织约束等关键信息
  • 上下文工程是 Vibe Coding 与 Spec Coding 的关键差异

    • 5.5 双向反馈

  • 生产现实反馈到规范演进中
  • 形成 SDLC（软件开发生命周期）闭环

    • 5.6 分支探索

  • 从同一规范生成多种实现方法
  • 探索不同优化目标：性能 / 可维护性 / 用户体验 / 成本

    • 六、spec-kit 工具详解

    6.1 什么是 spec-kit？

    GitHub 官方开源的 SDD 工具包，定位是辅助进行规范驱动开发。

  • 🔗 GitHub：https://github.com/github/spec-kit
  • ⭐ Stars：82.3k（截至 2026-03）
  • 核心价值：为 AI 提供元提示（meta-prompts），通过结构化输入约束 LLM 行为，产出更高质量的规范

    • 6.2 安装方法

    uv tool install specify-cli

    6.3 核心命令说明

    命令输入输出核心作用
    `/specify`模糊想法 / 一句话需求 / PRD`requirements.md`（需求规范）想法到结构化 PRD 的转化
    `/plan``requirements.md``plan.md` + `data-model.md` + `contracts.md`PRD 到技术实现计划的转化
    `/tasks`实现计划文档`tasks.md`（可执行任务清单）实现计划到具体编码任务的拆解

    6.4 spec-kit 元提示的约束机制

    spec-kit 的模板内置了一套 LLM 行为约束框架，确保产出质量：

    约束机制说明
    **防止过早技术细节**强制 LLM 关注"是什么"而非"如何实现"
    **强制标记不确定性**要求明确指出模糊之处，避免 AI 臆断
    **通过清单结构化思考**内置质量保证框架，促进自我审查
    **通过门禁强制合规**将原则转化为具体检查点，确保架构一致性
    **分层细节管理**保持文档高层次可读性，详细实现移至专门文件
    **测试优先思维**在实现代码之前定义契约和测试

│     └─ 反馈补充到规范文档                                         │

    八、对比其他 SDD 工具

    工具定位特点推荐场景
    **spec-kit**规范文档工具精细的元提示约束，规范产物高质量需要严格规范管控的项目
    **BMAD-METHOD**多 Agent 协作框架角色划分 + 流程协作 + 上下文工程复杂项目，多角色协作
    **OpenSpec**规范变更管理提案-审查-实现-归档的完整闭环规范演进管理需求强的项目
    **Kiro IDE Spec**IDE 集成工具开箱即用，适合 Vibe Coder 入门 SDD入门 SDD 概念

    推荐搭配：BMAD-METHOD + spec-kit

    BMAD 以 Agent 能力负责需求分析和设计协作，spec-kit 对 BMAD 内容进行精炼并输出高质量规范。

    9.4 完整开发流程

    ⚠️ 重要：建议每个阶段新开一个对话窗口，避免上下文窗口过大影响效果；每个阶段的产物需要 Review 正确性，避免错误传导影响最终结果。

    阶段 0：生成全局规范（Constitution）
    /speckit.constitution

    AI 生成 + 人工调整，产物为 .specify/memory/constitution.md，包含公司/团队级规范、仓库级规范。如果项目已使用 MDP-Context，会自动将其作为项目章程。

    阶段 1：产出需求规范（Specify）
    /speckit.specify <描述用户需求>

    产物目录结构：

    specs/<需求名>/
├── checklists/        # 需求分析过程中的检查清单
└── spec.md            # 需求文档（含需求分析、边界情况、[NEEDS CLARIFICATION] 标记）

    若对 spec.md 中内容有疑问，可用澄清命令补充模糊点：

    /speckit.clarify <针对 spec.md 中不符合预期的内容进行澄清>

    （kit-kiro 特有）评测需求质量：

    /speckit.eval-specify    # 对 spec.md 进行评测打分
    阶段 2：产出技术方案（Plan）
    /speckit.plan <根据 spec.md 生成技术方案，可补充额外要求>

    产物对比：

    模板产物文件
    **default 模板**`plan.md`（整体规划）、`data-model.md`（数据模型）、`contracts/`（接口文档）、`research.md`（技术选型决策）、`quickstart.md`（开发者说明）
    **kit-kiro 模板**`design.md`（包含设计文档，整合了上述内容）

    （kit-kiro 特有）评测方案质量：

    /speckit.eval-plan    # 对 design.md 进行评测打分
    阶段 3：任务拆解（Tasks）
    /speckit.tasks <根据 plan.md / design.md 生成代码实现任务>

    产物：tasks.md（拆分出的任务阶段）

    任务生成后，可执行一致性和质量分析（非破坏性）：

    /speckit.analyze <补充信息>

    该命令对 spec.md、plan.md/design.md 和 tasks.md 执行全面分析，检查三者的一致性。

    （kit-kiro 特有）评测任务质量：

    /speckit.eval-tasks    # 对 tasks.md 进行评测打分
    阶段 4：代码实现（Implement）
    /speckit.implement

    💡 最佳实践：如果 tasks 较多，建议分批执行，每次新开窗口：

    ```

    # 窗口 1

    /speckit.implement 完成 task1-2

    # 窗口 2

    /speckit.implement 完成 task3-5

    ```

    产出代码后，人工 Review 并检查 task 状态是否全部完成（建议在此阶段 commit）。

    如果项目使用了 MDP-Context，Implement 阶段会自动将 Spec 产物沉淀到 MDP-Context 中。

    （kit-kiro 特有）评测实现质量：

    /speckit.eval-implement    # 结合 tasks.md 对生成的代码进行评测打分
