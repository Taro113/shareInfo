1.1.1 需求简介

当前系统的核心功能是辅助一线完成快乐猴、小象、小象线下店的项目提报，构建工作流，支持整个选址团队在工作流中，完成项目审批和项目资料完善。本次需求的核心是在快乐猴现有提报流程上，增加店址报告的线上化能力，并优化当前的提报过程，更好地赋能选址团队完成线上化项目提报。

1.2 为什么选择SDD模式

目前，大多数人的使用方式仍停留在「对话式」阶段——描述需求、AI 生成代码、出错再改。这种方式看似高效，却存在一个根本性缺陷：AI 每次生成时，对项目的历史约束、业务规则和架构背景一无所知，它只知道你这次说了什么。

虽然上图有点夸张，但是也从侧面反映了大模型在缺乏约束和上下文的情况下，在研发过程中对开发人员造成的困境。

Specification-Driven Development（SDD），即规格驱动开发，正是为解决这一问题而生。其核心理念是：规格（Specification）才是资产，代码完全由规格派生。通过将项目架构、业务规则、编码规范显式沉淀为可复用的 Spec 文档，AI 每次生成代码时都能在完整的约束框架下工作。

在2026年，Harness Engineering又成了热门方向。但是从Vibe Coding到SDD再到Harness Engineering，最终的目标都是不断规范AI迭代工程的执行过程，建设一个可控、可验证、可持续优化的工程系统。而SDD模式，作为一个过渡性的阶段，既能快速解决Vibe Coding阶段的困扰，也可以作为Harness Engineering的基建，在项目快速提效方面，是一个不错的起点。

💡 提示：

实践建议：以下相关文件建议大家执行项目逻辑实践前读取一下各体系md内容，更好地了解指令的执行逻辑。

    执行过程：​

  • 输出：业务代码生成
  • 代码评分表：https://km.sankuai.com/collabpage/2753553839

    • 执行建议：​

  • 执行检查：建议通过/speckit.eval-implements指令检查执行结果
  • 会话管理最佳实践：
  • 不同task不要在同一会话中执行，一个任务新开一个会话
  • 如果会话执行完后出现空白屏，关闭当前项目并重启
  • 编译验证：
  • 模型提示编译通过可能实际未通过（存在幻觉），建议人工编译验证
  • 在提示词中追加编译要求，但不要完全依赖AI的编译结果
  • 代码质量保障：
  • 建立并维护项目的编码规范（通过MDP Context中的Rule体系）
  • 对于复杂逻辑，保持人工主导，AI仅辅助生成模板代码
  • 上下文压缩问题：控制单个会话执行task的数量（建议≤5个），分阶段执行任务

    • 主要问题分析：

    遇到的问题根本原因解决方案改进点
    Task执行过程中频繁触发上下文压缩，压缩后传输给大模型的信息可能不准确上下文长度限制控制单个会话执行task的数量，分阶段执行任务
    生成阶段存在代码报错(字段前后映射不一致，没有通过编译)​大模型幻觉问题在提示词中追加编译要求模型执行编译时间比较长，且存在幻觉，提示编译通过可能实际编译不通过，**建议人工编译。**
    代码生成不规范项目约束问题建立并维护项目的编码规范并持续完善可以建设团队级的编码规范，避免不同工程的重复建设问题
    会话执行完后出现空白屏，且无法开启新会话平台工具问题关闭当前项目并重启Catpaw问题，平台已经优化升级了一版，待进一步使用观察

    核心痛点：大模型上下限制、幻觉问题、以及项目本身约束不完善。

    实践建议：

  • 在大模型执行任务时，不同的任务不要在同一个会话中执行，一个任务新开一个会话。
  • 对于大模型的幻觉问题，增加提示词约束或者项目规则约束。

    3.4 SDD模式复盘与建议

    在执行过程中，我们分析了SDD模式下各阶段的模式差别，与相关协作方一块评估了对比传统模式的优劣势，以及在后续需求执行过程中的建议。

    维度传统模式SDD 实践对比及建议
    产研协作模式产品产出PRD，评审后研发产出技术方案，在技术方案阶段进行需求解读确认。在PRD之后，研发在生成需求解读文档阶段进行需求解读确认；且PRD要求对AI可读性强。**优势：**各方尽早对需求关键点进行理解和分析，提早确认和发现问题 **劣势：** - 在没有充分评审，尤其是逻辑复杂的需求，大家提前看文档未必能提出有效意见 - AI在短时间内生成的plan可能会遗漏需求关键点，研发同学可能对需求的澄清也可能遗漏 **建议：**针对复杂需求，在第一次评审后，可以搞二次确认，针对大家有问题的点，再进行review
    开发模式1. 技术方案阶段：基于PRD人工编写技术方案 2. 开发阶段：基于技术方案部分采用人工对话，部分人工编写。1. 技术方案阶段：使用spec kit生成执行计划和执行任务文件 2. 开发阶段： - 使用spec kit一次性生成需求代码 - 研发针对生成代码进行审查和优化 - 通过澄清任务信息迭代修正代码**优势：​** - 业务代码整体完成度较高，提效约60% **劣势：​** - 对研发人员要求较高，业务背景了解程度不够，或技术设计能力不够，会直接决定代码产出质量较低，需要多次修正 - 复杂逻辑生成质量不稳定 **建议：​** - 建立Spec编写最佳实践库 - 复杂逻辑保持人工主导
    自测CR模式研发同学开发时完成自测，联调结束提测前进行组内CR生成完代码研发同学进行一次CR，通过Test Agent完成自测，联调结束后组内CR**劣势：​** - AI生成代码需更仔细审查，CR成本增加 - 需要理解AI生成逻辑增加认知负担 **建议：​** - 建立AI代码CR检查清单 - 重点关注边界场景和异常处理
    前后端联调模式1. 接口文档在技术方案阶段提供 2. 前后端研发各自完成自测环节，进入联调1. 基于技术方案阶段的接口文档开发 2. 在代码生成完成后，考虑生成的代码，研发需要熟悉代码后再自测，自测效率低，直接进入联调。**劣势：​** - SDD模式下，前端生成代码时需要依赖接口文档，后端在生成代码后才会有接口文档，协作模式上存在冲突 - 联调阶段排查问题的时间变长，联调效率降低。 **建议：​** - 需要外部工具支撑，在代码生成之前完成接口协议文档 - 在代码生成后增加研发CR环节，CR完成后进入联调。
    测试模式1、测试用例人工编写，在联调阶段提供 2、测试阶段测试用例通过人工执行，人为发现问题1、使用AI基于spec文档&prd生成可执行的测试用例[AI生成测试用例](https://km.sankuai.com/collabpage/2754762541) 2、通过AI测试助手-自动检查代码风险以及执行测试用例，输出测试结果[AI 问题分析](https://km.sankuai.com/collabpage/2754389656)**优势：​** - 节省测试用例编写时间，QA只需要进行审查修改即可。 - 相比人工测试，AI测试助手能针对代码进行更完整的风险检查，发现人为无法覆盖到的风险点。 - 支持接口自动调用，结合代码静态检查+接口返回信息判断用例是否符合预期。 - 支持自动生成测试报告（场景，用例执行结果，风险，定位代码，改进方案） **劣势：​** - 生成可执行的测试用例强依赖完整&准确的spec文档。 - AI测试助手检测的风险较多，排查成本较高。 - 超出模型能力边界的用例，仍需要人工补位。 - 并发条件竞争、死锁； - 数据一致性； - 性能瓶颈、内存泄露； - 依赖特定数据分布或极端场景的缺陷。 - 复杂场景（校验点多）可能会遗漏问题。 **建议：​** - 提升用例质量 - 提前明确使用ai检测的用例类别，不适合的用例由人工补位 - 增加需求文档/spec文档准入标准（全+准） - 增加用例覆盖度评估环节，对spec的覆盖（ai） - 完善执行能力 - 增加评估器，执行二次风险评估与验证，减少误报 - 增加复核机制，检测修复结果&是否带入新问题。 - 风险进一步分类（缺陷类（高+中+低风险）、建议类），减少排查成本。 - 建立“漏检&误报问题回溯”机制，对人工发现但 ai测试助手未识别的问题和ai测试助手误报的问题，沉淀成“典型缺陷+高质量用例”的样例集存储在长期记忆中，后续在新项目AI测试助手 前作为 few-shot 示例提供给模型，逐步提升对类似问题的敏感度。

    3.5 SDD模式优缺点分析

    3.5.1 SDD 模式的亮点 ✅

    亮点一：研发效能显著提升，工时节省超40%​

    SDD模式通过AI辅助代码生成和自动化流程，实现了研发效率的大幅提升。

    关键数据支撑：​

  • 开发阶段：前端从17PD降至3PD，后端从20.75PD降至4PD
  • 测试阶段：通过AI测试助手发现39个问题（29个真实缺陷），覆盖率提升
  • 资源释放：标准功能开发效率提升75%，团队整体产能增加

    • 亮点二：工程协作流程标准化，质量可追溯

    SDD模式将开发流程结构化为Constitution → Specify → Plan → Task → Implement → CR → Deploy七个标准化阶段，每个阶段都有明确的产出物和验收标准。

  • Spec文档驱动：spec.md、requirements.md作为唯一事实来源，确保需求理解一致
  • 自动化生成：从需求到代码的完整链路自动化，减少人工传递误差
  • 过程可追溯：每个任务都有对应的文档记录和执行日志，便于问题回溯
  • 规范内置：通过MDP Context的Rule体系，将编码规范、架构约束内置到AI生成过程中

    • 亮点三：AI与人工深度协作，而非简单替代

    SDD模式不是"一键生成代码"，而是建立了AI生成+人工Review的深度协作机制：

  • AI负责标准化：CRUD代码、模板代码、重复性逻辑由AI高效生成
  • 人工专注复杂：业务逻辑设计、架构决策、异常处理由人工主导
  • 混合开发模式：标准功能（AI生成+人工Review）+ 复杂功能（人工设计+AI辅助）
  • 智能测试辅助：AI测试助手基于spec文档自动发现代码风险，人工补充边界场景

    • 这种协作模式既发挥了AI的效率优势，又保留了人工的专业判断，避免了纯AI开发的"幻觉"问题。

    亮点四：项目资产持续沉淀，形成可复用的知识体系

    SDD模式的核心价值在于建立了可复用的项目知识资产体系：

  • Context体系：沉淀项目架构、业务规则、核心概念、依赖关系，让AI快速理解项目背景
  • Rule体系：汇集编码规范、数据库设计规范、架构分层约束，确保代码质量一致
  • Spec文档库：需求文档、技术方案、测试用例形成沉淀，可以用于追溯问题，也便于新人上手项目
  • 问题沉淀机制：联调问题、测试缺陷、CR意见持续沉淀，形成"典型缺陷样例集"

    • 这些资产在新项目中可以复用，形成"越用越智能"的正向循环，为团队的长远发展奠定基础。

    四、架构决策与推广策略

    4.1 核心结论

  • 模式价值确认：​ SDD模式在标准功能开发上效果显著（效率提升75%），值得在适合场景推广
  • 关键成功因素：​ 前期Spec质量、Context建设/Rule建设、研发成员SDD熟悉程度是成功关键
  • 主要风险点：​复杂逻辑质量不稳定、自测联调成本增加。
  • 适用边界：​ 适合标准CRUD功能（占比>60%），不适合复杂业务逻辑和历史债务改造

    • 4.2 落地建议

    建议一：AI存在认知问题，人工需要做好辅助引导

    在开发过程中，我们核心的目标是使用工具更好的达成结果，不断完善过程，达成最佳实践，并不是去考验AI的能力。

    建议二：关注执行过程，深入理解执行原理

    首次需求实现的时候，建议大家关注整个执行过程，可以更快了解模式的运行过程，更好的使用SDD模式辅助开发，遇到问题也能从原理角度分析解决。

    建议三：Spec 质量决定代码质量，必须人工重点审核

    spec.md、plan.md 和 design.md 是代码质量的上游。描述越精确，AI 生成代码质量越高，但 AI 自己生成的 Spec 不一定准确，需要开发者亲自 review 并修正。

    建议四：Rule 必须前置建立，变更链路是重点

    DB 变更规范（Entity/BO/SQL 三处同步）、灰度控制规范、LION 配置命名等必须在 Constitution 阶段之前就位。这类规则一旦缺失，代码生成质量可能会大打折扣。

    建议五：Context 持续丰富，库表模型不依赖临时文件

    库表模型、业务规则、AI 盲区清单需持久化维护在 .mdp/context/ 下，不能依赖 plan 阶段生成的临时文件。每次需求 Specify 时同步更新。

    建议六：Plan 需要 3-5 轮迭代，关键决策不交给 AI

    期望 plan 一次到位是不现实的。设计模式的选择、复杂逻辑的拆解方式，这些关键决策必须在 plan 阶段由人工明确给出，不能让 AI 自行决定。

    建议七：复杂场景人工主导，AI 仅辅助

    跨系统问题排查、历史债务处理、复杂按钮逻辑——这些场景超出了当前 Spec Coding 的有效边界，AI 只能辅助，人工判断不可省略。强行依赖 AI 生成只会增加返工成本。

    4.3 规模化落地考量

    试点推广：​ 选择标准CRUD功能占比>80%的需求进行试点

    分阶段实施：​ 先从简单需求开始，逐步扩展到复杂需求

    持续优化：​ 建立团队开发规范标准以及项目级业务背景知识，沉淀需求SDD模式实践文档（短期内所有试点需求），持续改进模式

    风险管控：​ 建立监控机制和应急预案[^建立监控机制和应急预案：本次需求是先定了大致排期，再推广的SDD提效，时间相对充裕。建议大家新试点需求时，估时不要太激进。]，确保项目成功

    • 提问1：传统方式技术方案产出和sdd模式技术方案产出，耗时对比情况如何?

    答：SDD模式下技术方案产出比较快，因为模板是相对固定的，只需要人工澄清清楚相关技术细节即可。但是会有一定的上手成本，但是基本短期内就可以熟悉执行流程。

    此外，从整体项目开发周期看，大模型生成的技术方案直接用来生成代码，可以避免人工传递信息的误差。从整个研发流程来看，耗时是降低的。

    提问2：context、rules生成时，人工占比耗时如何？生成的规则内容质量如何？

    答：context生成比较快，生成时同时会生成公司级的rules。项目级rules生成时间耗时比较长，因为执行过程中会读取当前业务代码，整个生成过程差不多是小时级的。

    从本次需求的执行情况看，生成的规则内容质量是不错的。不过，规则是基于当前代码的，不一定是最佳实践，可以在迭代过程中通过update-rule的方式不断完善。

    提问3：产品prd需要如何适配新模式下的需求开发？

    答：本次实践过程中，基于specify生成的spec.md格式模板，创建了一个skill用来生成模板化的产品文档。和产品协作使用新模式编写prd，便于spec模式使用。

    提问4：不同项目生成的rules是否有差别？公司级的rules生成是否会根据提示词或上下文不同而导致生成效果不同？

    答：有差别，rules是基于当前项目的代码生成的。公司级的rules是在项目初始化阶段生成的，是统一的，不同项目间没有差异

    提问5：任务执行时拆分的粒度有什么建议？

    答：本期我们是人工判断生成的，但是也可以让agent自动拆分成subagent的方式去执行。我们实践过程中还有经验是：可以基于代码分层去拆分任务，也是可行的。

    提问6：如何保证代码生成的质量？

    答：在项目联调前，通过单测覆盖的方式解决代码中的问题。

    提问7：中间过程中，产出的md文档是否会详细review？

    答：会详细review，而且开发时间中的主要精力应该是review中间产出的md文档，因为文档质量决定最终的代码质量。开发过程中大模型生成文档耗时是比较少的，主要耗时时间其实就是人工review的时间。
